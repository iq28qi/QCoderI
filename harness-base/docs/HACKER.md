# Профиль «Хакер»

Профиль ведёт локальный реверс-инжиниринг и аудит: сам запускает фоновый анализатор, читает отчёты, вносит правки, собирает и проверяет результат. Каждый вывод о бинарнике опирается на адрес, имя функции и фрагмент инструкций или псевдокода из сохранённого отчёта. Настройки профиля находятся в `assets/team/binary-analysis.js`, `assets/team/hacker-preset.yml` и в `hacker_prompt` внутри `scripts/build.py`.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `binary_analyzer_status` | Найти локальные headless Ghidra и IDA, проверить совместимый JDK, ничего не запуская. |
| `binary_analyze` | Импортировать файл в Ghidra или IDA, выполнить автоанализ, сохранить базу, отчёт `analysis.json`, журнал `run.json` и `process.log`. Опциональный `query` сразу добавляет доказательства. |
| `binary_query` | Переоткрыть сохранённую базу (`-process` в Ghidra, готовый `.i64` в IDA) и ответить на новый вопрос без повторного анализа. Возвращает сводку и путь к отчёту `query-*.json`. |

Файл анализа не запускается: работают только `analyzeHeadless`/`idat` в режиме автоанализа. Каталог запуска — `QCoderI-Analysis/run-*` внутри выбранной рабочей папки; исходник копируется туда как снимок, SHA-256 которого фиксируется в журнале.

Поиск установок: параметр `install` (требует явного `engine`) либо переменные `QCODERI_GHIDRA_HOME`, `GHIDRA_HOME`, `QCODERI_IDAT`, `IDA_HOME`; для Ghidra дополнительно `java_home`/`JAVA_HOME`. Если JDK не подходит, статус сообщает об этом отдельно, а не сообщает «Ghidra не найдена».

## Поля запроса

`query` передаётся объектом в `binary_analyze` и `binary_query`; движок получает его как JSON в `QCODERI_ANALYSIS_QUERY`.

| Поле | Смысл | Границы |
|---|---|---|
| `function_name` | точное имя функции | до 256 символов |
| `name_query` | подстрока или регулярное выражение по имени | до 256 символов |
| `regex` | трактовать `name_query` как regex | — |
| `address` | шестнадцатеричный адрес; по умолчанию VA | до 32 символов |
| `address_is_offset` | адрес задан как смещение от image base | — |
| `decompile` | включить псевдокод, если декомпилятор доступен | — |
| `xrefs` | вызывающие, вызываемые и ссылки на функцию | по умолчанию включено |
| `callgraph_depth` | ограниченный граф вызовов от найденных функций | 0–3 |
| `instruction_limit` | инструкций на функцию | 1–1024, по умолчанию 128 |
| `strings_query` | поиск определённых строк по тексту | до 256 символов |
| `string_limit` | сколько строк вернуть | 1–256, по умолчанию 32 |
| `matches` | сколько функций развернуть | 1–16, по умолчанию 4 |

Один из селекторов (`function_name`, `name_query`, `address`) или `strings_query` обязателен, иначе запрос отклоняется с точной диагностикой. Неизвестные поля и значения вне границ отклоняются до запуска анализатора.

## Отчёт

`analysis.json` и `query-*.json` содержат:

- `engine`, `format`, `architecture`, `image_base`, `analysis_complete`;
- `sections` (имя, адрес, размер, права) — до 256;
- `function_count` и первые 512 функций;
- первые 512 импортов;
- `query`, `address_convention`;
- `function_details`: имя, адрес (VA), размер, `matched_by`, инструкции, `truncated`, `callers` (адрес вызова + функция), `callees`, `decompiled` (`available`, `language`, `code` или причина отказа), `callgraph`;
- `string_matches` при `strings_query`.

Псевдокод ограничен 12 000 символов на функцию и помечается `truncated` при усечении. Отсутствие символов и строк означает, что назначение функции остаётся гипотезой; отчёт это не скрывает.

`binary_query` возвращает сводку: имена, адреса, число инструкций, доступность декомпилятора, количество вызывающих и вызываемых, число узлов графа. Полные инструкции и псевдокод остаются в отчёте — их читают через `read` и `grep`, чтобы не терять содержимое в усечённом выводе инструмента.

## Правила доказательств

1. Сначала идентичность: путь, формат, архитектура, `image_base`, SHA-256 снимка.
2. Различайте файловое смещение, RVA и VA. Адреса в отчётах — VA внутри загруженного образа; при переносе на живую базу модуля пересчитывайте через `image_base`.
3. Значения конкретной сборки держите в одном именованном конфиге или резолвере, проверяйте по границам модуля.
4. Не используйте найденный в интернете дамп как раскладку текущей сборки: совпадение имени функции не подтверждает её поведение.
5. Частичный или устаревший снимок данных отбрасывается целиком.
6. Для изменений фиксируйте исходное состояние, замену, предусловия и откат; результат подтверждается чтением после записи.

## Аудит кода, сайта и сервера

Профиль разбирает предоставленный код и конфигурацию и выдаёт: конкретное место (файл, строка, параметр), первопричину, последствия, исправление и проверочный тест. Для сервера достаточно обезличенной конфигурации и сведений об образе — приватные ключи не требуются. Динамическая проверка на чужом стенде выполняется только при наличии разрешения и доступа, предоставленных владельцем.

## Измерения в игре

Замер фиксирует единицы, базу сравнения, число повторов и условия. Одиночный замер без повторяемости не считается подтверждением. Изменения в памяти и патчи описываются с точной сборкой, исходными байтами и откатом.

## Проверка

`tests/binary-analysis-native.mjs` собирает тестовую программу (`gcc.exe`), поднимает реальный AgentLoop и Ghidra, затем проверяет: обнаружение профиля, инвентарь, поиск по имени, адресу, вызывающих и вызываемых, граф вызовов, псевдокод, поиск строк и переоткрытие базы через `binary_query`.

```powershell
$env:JAVA_HOME='D:\reverse-tools\jdk21'   # совместимый JDK для Ghidra
node .\harness-base\tests\binary-analysis-native.mjs
```

Без совместимого JDK или Ghidra тест печатает `SKIP` (принудительный запуск — `QCODERI_REQUIRE_GHIDRA_TEST=1`). Ветка IDA в живом тесте не проверяется, если `idat64.exe` не установлен: список функций, псевдокод Hex-Rays и переоткрытие `.i64` используют те же поля отчёта, но требуют установленной IDA с IDAPython.

## Ограничения

- Статический анализ не доказывает поведение, зависящее от времени выполнения; для этого нужен отладчик и разрешённая среда.
- Hex-Rays может отсутствовать или быть нелицензированным: тогда `decompiled.available=false` с причиной, а не пустой псевдокод.
- `-process` в Ghidra требует корректного имени программы в проекте; при переименовании проекта повторный запуск `binary_analyze` остаётся запасным путём.
- Автоматический поиск уязвимостей по отчёту — это обзор кандидатов (небезопасные копирования, арифметика, импорты, строки), а не доказательство эксплуатируемости. Эксплуатируемость подтверждается отдельной проверкой в разрешённой среде.
- Отчёты ограничены по объёму; для больших бинарников используйте несколько узких запросов вместо одного широкого.
