# Что перенести из Flecten в QCoderI

Статический обзор от 14 ноября 2026 года. Проверен Flecten на коммите
`c46a765c758ab2aa1714d9584aa87791920f0b95`.
Исходники прочитаны без установки зависимостей и запуска стороннего приложения.
Функции Flecten в рабочую сборку QCoderI в рамках этого обзора не переносились.

## Вывод

Наибольший эффект дадут управляемая работа в фоне, память подтверждённых
пожеланий, проверка визуального результата и понятное восстановление файлов.
Подходящие механизмы следует адаптировать к существующему Cordis/React-ядру.
Flecten использует Bun/TypeScript/Svelte, поэтому его интерфейс и ядро нельзя
подключить к нашей сборке простым копированием каталогов.

## 1. Общение во время выполнения

Flecten отделяет Talker от Worker: независимые циклы, start/steer/status/stop,
события живых карточек и восстановление хронологии после открытия чата.
Промежуточный вывод инструмента показывается без дополнительного запроса модели.

У QCoderI уже есть фоновые jobs, команда исполнителей и штатные
`send_message`/`interrupt_agent`. Использовать их как основу, добавив понятный
пользовательский сценарий: обсуждать задачу, уточнять требования и останавливать
только исполнителя. Не дублировать планировщик команды.

Проверить: уточнение во время долгой команды, независимую отмену, порядок событий
после перезапуска и отсутствие автоматического повторного выполнения команды.
Разделение контекстов требует дополнительных модельных запросов; экономию не обещать.

Источники: [контракт](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/docs/TALKER-WORKER.md),
[реализация](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/src/app/conversation.ts).

## 2. Память проекта с происхождением записей

Заимствовать типы preference/lesson/decision/procedure, ключ и ревизию записи,
подтверждающую цитату, ограничение контекста и отзыв устаревшей информации.
Текущий пользовательский запрос должен иметь приоритет над сохранённой памятью.

В QCoderI постоянный системный промпт и проектные инструкции уже есть.
Следующий полезный слой — отдельный редактируемый банк пожеланий и исправлений
проекта: например, «не открывать тестовые окна», ограничения целевой игры,
согласованные пропорции персонажа и требования к рендерам.
Не копировать туда всю историю, ключи или догадки о предпочтениях человека.

Проверить: применение в новом чате, изоляцию проектов, обновление и забывание,
приоритет новой инструкции, невозможность выдать текст инструмента за слова пользователя.

Источник: [память](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/docs/MEMORY.md).

## 3. Действия по актуальному наблюдению и передача управления

Самый близкий к повторному использованию блок — ComputerSession: observationId,
последовательная очередь, смена владельца управления и отмена ожидающих действий.
Отдельное обновление картинки для человека не подменяет наблюдение исполнителя.

У QCoderI уже есть Windows UI Automation, клавиатура/мышь, проверки окна и снимки
после действий. Добавить идентификатор наблюдения и общую блокировку ввода между
чатами/агентами, панель актуального экрана, «Забрать управление» и «Продолжить».
Не допускать одновременного ввода двух исполнителей в один физический рабочий стол.

Готовый backend Flecten работает только с отдельным Linux-дисплеем через Xvfb и
xdotool. Он не заменяет наш Windows-драйвер и не даёт поддержку всех приложений.
Неоднозначно завершившееся действие нельзя автоматически повторять.

Источники: [ComputerSession](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/src/marketplace/modules/computer-use/session.mjs),
[границы](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/docs/COMPUTER-USE.md).

## 4. История изменений и выборочный откат

Взять принцип хранения before/after, проверки текущего хеша перед восстановлением,
выборочного отката и отдельного Git-хранилища, не изменяющего индекс пользователя.
Flecten пропускает конфликтующие файлы вместо молчаливого затирания новых правок.

Штатный session-checkpoint-policy QCoderI сохраняет журнал сессии перед запросами
и действиями; это другой механизм, он не является версией файлов для Undo.
Для нашего интерфейса нужны список изменённых файлов, diff и откат конкретного
действия. В 3D нужны версионные копии .blend и сравнение рендеров: текстовый diff
не объяснит изменения бинарной сцены. Откат файлов не отменяет внешние действия GUI.

При адаптации ShadowGit проверить Windows-пути, CRLF, symlinks/junctions, файлы
без Git и большие бинарные ассеты; в исходнике используются /dev/null и POSIX-defaults.

Источник: [checkpoint implementation](https://github.com/AnnenkovLabs/flecten/tree/c46a765c758ab2aa1714d9584aa87791920f0b95/src/store/checkpoints).

## 5. Проверяющий результат по требованиям пользователя

В Twin полезен механизм проверки этапа и итогового результата, возврата на
доработку, учёта расходов и ограниченного количества повторов. Сам персонаж и
имитация манеры речи имеют меньший приоритет для QCoderI.

Предлагаемая адаптация для 3D: проверяющий получает исходные референсы, требования,
несколько реальных ракурсов и отчёт геометрии. Выдаёт конкретные замечания по
сходству, силуэту, материалам и техническим дефектам. Исполнитель исправляет
замечания в пределах заданного бюджета; пользователь видит нерешённые проблемы.
Существующие blender_run/views и share_image дают основу для такого цикла.

Это предложение расширяет Flecten: его Twin получает ограниченный набор последних
изображений инструментов, а не полноценную специализированную оценку 3D-ассета.
Проверка моделью не доказывает точное сходство и не гарантирует качество.

Источник: [Twin](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/docs/TWIN.md).

## 6. Интерактивные результаты в чате

Адаптировать sandboxed HTML для таблиц проверок, графиков, сравнения ракурсов и
вариантов материалов. HTML работает в отдельном iframe с запретом сети; действия
наружу проходят через ограниченный проверяемый протокол.
В QCoderI уже есть карточки изображений, видео и увеличение оригинала.
Новый HTML-режим должен дополнять их и не получать Electron/Node API.

Источник: [sandbox и CSP](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/ui/src/lib/markdown/sanitize.ts).

## 7. Второй этап: IDE, словарь и голос

- IDE: редактор с вкладками, поиск/замена с просмотром изменений, управление Git,
  сохранение с проверкой конфликтов. У нас уже есть файлы и терминал; развивать
  существующие панели, а компоненты Svelte переносить по поведению.
- Словарь: локальные названия объектов, материалов и терминов с алиасами и
  исправлением раскладки. Исходное сообщение человека сохранять буквально.
- Голос: диктовка через API либо локальные faster-whisper/Vosk. Это запись в
  черновик, не полноценный голосовой разговор. Windows-путь потребует отдельной проверки.

Источники: [IDE](https://github.com/AnnenkovLabs/flecten/tree/c46a765c758ab2aa1714d9584aa87791920f0b95/ui/src/components/ide),
[словарь](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/src/dictionary/match.ts),
[голос](https://github.com/AnnenkovLabs/flecten/blob/c46a765c758ab2aa1714d9584aa87791920f0b95/docs/VOICE.md).

## Что не переносить без изменений

- Полное ядро приложения: другая среда и UI, дублирование уже работающих сервисов.
- Автоопределение возможностей как готовое решение нашей проблемы с фото:
  discovery-models.ts читает отдельные поля API, но это не подтверждение того,
  что конкретный маршрут действительно передаёт изображение модели.
  Сохранить наши правила приоритета и проверки реальным изображением; добавить
  понятный статус «из каталога / задано вручную / проверено на этом маршруте».
- Автоматическое использование более дешёвой модели для визуальной проверки без
  проверки её возможностей и сохранения выбранного пользователем качества.
- Гарантии улучшения качества, экономии и универсального управления: статическое
  наличие кода и тестов их не доказывает. README обозначает проект как alpha.

## Рекомендуемый порядок

1. Актуальность наблюдений, единый владелец ввода, ручная передача управления.
2. Память проекта и проверка реальных результатов 3D с лимитом доработок.
3. Общение во время работы с независимой остановкой исполнителя.
4. История изменений, конфликтобезопасный откат и версии бинарных сцен.
5. Интерактивные отчёты, развитие IDE, словарь и голос.

Каждый этап выпускать отдельно с воспроизводимыми скрытыми проверками Windows.
Не добавлять сразу несколько постоянно вызываемых моделей: отдельно измерять
стоимость, задержку и долю исправленных ошибок на реальных задачах.
